# Is 0SFS the most advanced open-source browser flight simulator?

Assessed 25 October 2026. This is a source and documentation review, not a comparative flight test or performance benchmark. Competitor revisions are pinned below. 0SFS findings describe the local development checkouts, including existing uncommitted work, rather than claiming every feature is live on the public site.

## Finding

**0SFS has a credible leadership claim on the combined capabilities that motivated this review: modern rendering, physical sky, real-world scenery, flight dynamics and browser controls.** No reviewed competitor documented the same combination of WebGPU, JSBSim WASM, a real-world globe with optional Google Photorealistic 3D Tiles, Rust world-computation cores, optional shared-memory sky threads, terrain contact, aircraft sound, phone pairing and a two-pilot multiplayer preview. On those priorities, the reviewed evidence favors 0SFS. This is a qualitative assessment of the surveyed set; an exhaustive worldwide ranking and comparative flight fidelity remain unestablished.

**Aeronaut's overlap in JSBSim WASM and Google 3D Tiles does not establish comparable overall capability.** The earlier inference that this overlap meaningfully rebutted 0SFS's overall claim was too strong. The focused comparison below finds substantial differences in the renderer, sky implementation, sound, phone control, ground handling and keyless access. YSFLIGHT's original simulation engine, community add-ons, replay persistence, offline play and WebRTC multiplayer warrant comparison on simulation breadth. Force's interactive cockpit and RCForge's aircraft workbench also deserve credit on their respective dimensions. None of those individual strengths establishes an overall peer to 0SFS on the combined criteria above.

For the landing page, use **“Serious flight. One browser tab.”** followed by the concrete capabilities. For a technical description: **“An open-source browser flight simulator combining WebGPU graphics, JSBSim flight dynamics, real-world scenery and Rust WebAssembly world-computation cores.”** Explain the optional shared-memory sky mode where there is room. “One of the most technically ambitious” can be an explicitly identified assessment; a universal first-place ranking needs a defined test and stronger evidence.

## What counts

- A browser simulator executes interactive simulation and rendering in the browser. A remote desktop stream, native engine with a web instrument panel, or a flight tracker is a different category.
- Open-source **application code**, aircraft assets, map services and hosted-service access are separate questions. A permissive rendering library does not open-source the application built on it. Public code with a noncommercial restriction does not meet the [Open Source Definition](https://opensource.org/osd), particularly its redistribution and fields-of-endeavor requirements.
- “Advanced” includes flight-model validation, aircraft systems, terrain contact, cockpit interaction, scenery, multiplayer, extensibility, reliability, accessibility and measured performance. WebGPU and Rust describe implementation choices; they do not establish aerodynamic fidelity or a better experience by themselves.
- For this brief, modern graphics, the physical atmosphere, integrated world/ground simulation, sound and paired-phone controls carry particular weight. Free hosted access and keyless startup are additional product advantages; a self-hosted open-source browser application still qualifies for the survey. State these priorities when making an overall assessment rather than assigning an unexplained universal score.
- A supported optional implementation counts as an available path, not as the default. A proposal counts as future work. Unverified claims remain unverified; absence from a README is not proof of absence from a project.

### Aeronaut: shared components and delivered capabilities

Three.js supports [WebGPURenderer](https://threejs.org/docs/pages/WebGPURenderer.html), but Aeronaut's inspected [`src/engine.js`](https://github.com/vinny-palumbo/FlightSim/blob/4a47e8a5652657427df40490f1156ce8464cefbb/src/engine.js#L16) constructs `T.WebGLRenderer`. Its Google view separately instantiates a Cesium viewer. A library's available renderer does not establish that an application uses it.

The following comparisons use the pinned Aeronaut revision and the local 0SFS implementation described below. Audio and remote-control checks searched all 11 JavaScript/JSX application files under `src/`, the dependency manifest and the tracked file inventory. Findings of absence are scoped to that review, not promises about future versions or every dependency's internals.

| Capability | 0SFS implementation | Aeronaut evidence |
|---|---|---|
| WebGPU | Supported rendering path, with WebGL fallback | Explicit Three.js `WebGLRenderer`; no application WebGPU path found. |
| Sky and astronomy | [Clear-atmosphere scattering, sky/ground illumination, solar/lunar models and stars](https://github.com/foss-earth/sky/blob/main/README.md); partial Rust/WASM port with optional shared-memory threads | Google flight view uses a Cesium viewer without a comparable custom atmosphere/astronomy implementation or controls found in the application source. Setup uses a blue background and fog. This does **not** establish that Cesium renders no atmosphere. |
| Aircraft audio | [AudioWorklet + WASM synthesis](https://github.com/0SFS/sound/blob/main/docs/sound.md), driven by aircraft/engine state, with spatial effects and tire cues | No application audio implementation, declared audio dependency or tracked audio asset found in the inspected revision. |
| Paired-phone controller | Separate browser controller with QR pairing | Same-screen touch buttons are implemented in [`src/main.jsx`](https://github.com/vinny-palumbo/FlightSim/blob/4a47e8a5652657427df40490f1156ce8464cefbb/src/main.jsx); no phone-pairing or remote-control transport found. |
| Ground operations | Streamed-terrain input to JSBSim ground contact and runway starts | README explicitly excludes supported takeoff/landing and terrain/building contact. |
| Keyless flying | Raster imagery/elevation path works without a Google key; Google 3D Tiles remain optional and require a key | README requires the user's Google key with billing enabled and offers no offline practice mode. |

**Public access:** no advertised free public Aeronaut play URL was found in its README, repository homepage metadata or the targeted demo searches. GitHub metadata reported no homepage and no GitHub Pages deployment; the README provides local startup and manual hosting instructions, and says CI only tests/builds. This is evidence of discoverability and setup friction, not proof that no external deployment exists. Google key/billing requirements remain a separate barrier even if somebody hosts the application.

**Assessment:** Aeronaut supplies useful prior art for integrating JSBSim and photorealistic scenery. It is weak evidence against 0SFS's leadership across the full feature set above. The sky comparison establishes a substantial difference in application implementation; perceived visual quality still needs matched screenshots or flights, and neither project's physical accuracy follows automatically from complexity.

### Other comparisons that change the answer

**FlightGear:** the [official project](https://www.flightgear.org/about/features/) targets Windows, macOS and Linux. It is the appropriate depth benchmark for aircraft, systems, weather and integrations, rather than a direct browser application in its standard distribution. [tcp-flightgear](https://thomass171.github.io/tcp-flightgear/tcp-flightgear.html) experiments with migrating FlightGear components/scenery into the browser; that does not demonstrate the whole current FlightGear simulator running there.

**GeoFS:** the [official About page](https://www.geo-fs.com/pages/about.php) describes a browser simulator using CesiumJS. That open-source dependency does not establish an open-source GeoFS application. No complete OSI-licensed simulator source distribution was established here, so it is a browser product benchmark rather than a verified open-source peer in this survey.

**Dimar Tarmizi's Web Flight Simulator:** its [current license](https://github.com/dimartarmizi/web-flight-simulator/blob/main/LICENSE) explicitly restricts commercial use. Public source is available, but this is not an OSI-open-source peer under the definition above. Its visual/gameplay quality still matters when comparing the experience visitors can get in a browser.

**SkySim:** [revision a31864f](https://github.com/vishwagw/Sky-Sim-drone-simulator-3.0/tree/a31864f999418531775980b879979ce4c57e791d) has an **MIT license**, despite older search results describing a noncommercial license. Its README describes a browser WASM preview and ArduPilot/PX4/Betaflight integration, but explicitly assigns firmware SITL and heavy ML to a native agent server. The browser demo link is still an `OWNER/REPO` placeholder in the inspected README; browser availability and firmware integration were not tested. This is adjacent prior art, not evidence of a completed browser-only ArduPilot integration. Adding an ArduPilot bridge alone would not establish uniqueness.

Simulation frequency is separate from render FPS. The previous landing page's unconditional 120 Hz claim was stale. |
| Rust world computation | [Engine](https://github.com/foss-earth/engine/blob/main/README.md) has raster, terrain and ground Rust/WASM twins; the [renderer](https://github.com/foss-earth/renderer/blob/main/README.md) has Google preparation; [sky](https://github.com/foss-earth/sky/blob/main/sky-WASM/README.md) has a partial atmosphere port. JavaScript/TypeScript integration remains significant. |
| Physical sky and astronomy | [Sky owner](https://github.com/foss-earth/sky/blob/main/README.md) implements clear-atmosphere scattering and illumination, solar/lunar position models and stars. Physical-model scope and perceived realism should be assessed separately. |
| Shared-memory multithreading | The sky core has a real shared `WebAssembly.Memory`, atomic row scheduling, a coordinator and helper workers. | Faster because it has threads | Not established for whole-app frame time. The sky README reports faster warm kernels, but no frame-time improvement beyond A/A spread and increased total sky CPU in the tested configurations. Those results cannot become a general FPS or battery claim. |
| Real-world scenery and ground contact | [FOSS Earth relationship](https://github.com/0SFS/fly/blob/main/docs/foss-earth-relationship.md) and [ground contact](https://github.com/0SFS/ground-contact/blob/main/docs/ground-contact.md). Raster maps/elevation do not need a Google key; photorealistic tiles require one and retain provider terms. Availability is not uniform photogrammetry everywhere or validated collision against every feature. |
| Aircraft, systems, sound and pilot effects | Current catalogue has C172, Vision Jet and experimental F-35B families. ## How to support a stronger claim

Publish a dated comparison and reproducible tasks rather than choosing weights after seeing who wins:

1. **Flight fidelity:** trimmed cruise, throttle response, stall/recovery, climb, landing and wind response, against disclosed aircraft reference data and tolerances. Using JSBSim validates neither custom aircraft data nor a particular engine installation automatically.
2. **Ground interaction:** runway start, taxi, braking, takeoff and landing on the same declared terrain source, with streamed-data failure behavior recorded.
3. **World and systems:** real scenery coverage, controls, cockpit functionality, avionics, engine/fuel behavior, available aircraft and interoperability; distinguish implementations from roadmap items.
4. **Browser performance:** same hardware/browser, viewport/pixel ratio, scenery, cache state, physics rate and tasks. Report startup-to-control, median/p95 frame time, memory, network and worker/kernel modes. Test a laptop and a phone; compare both a common rendering path and each product's best supported path. Do not infer efficiency from language or API names.
5. **Reproducibility:** license text, source revision, build instructions, test evidence and failures. Independently rerun the leading competitors. A search cannot prove exhaustive coverage of all open-source projects.

Until then, **the architecture combination is the strongest defensible story**. A future ArduPilot integration would strengthen it if the flight loop, takeover, timing and failure behavior are demonstrated, but does not establish universal superiority merely by appearing on a roadmap.

## Search and source method

Started with the September survey in [Open-source competitors](open-source-competitors.md), then searched for open-source browser/WebGL/WebGPU simulators, JSBSim/WASM, Rust, YSFLIGHT browser ports, and ArduPilot/PX4 browser simulators. Search engines were discovery tools; project source, README files, licenses, official product pages and OSI's definition supplied the substantive evidence. No star-count ranking was used.

Read pinned README/license texts for every pinned project above; inspected Aeronaut's `src/engine.js` (`THREE.WebGLRenderer`) and `src/jsbsim-flight.js`, OpenSkyFlight's `js/camera/FlightController.js` (camera-position integration), and rlefko's `src/main.ts`, `src/rendering/WebGPURenderer.ts` and `src/physics/FlightDynamics.ts`. The Aeronaut follow-up also checked all 11 application source files for audio and remote-control implementation indicators, read its UI/world/dependency files, and checked public repository hosting metadata. Its `world.js` contains a gradient-sky helper, but the flight engine imports only `createPlane` from that file; the helper is not evidence of an active flight sky. Source/file inventories, downloaded texts and scoped search results are retained locally in ignored `research/build/competitor-evidence/`. These targeted reads establish specific architecture facts, not complete code audits. Older articles and search snippets were cross-checked because they can be wrong about current licensing and implementation.
